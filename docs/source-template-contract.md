# Source-template workflow contract (E21)

The source-template session API is a bounded local workflow over the existing ingestion, PageModel, review and template-version contracts.

- `POST /api/source-template-sessions` requires `disclosure_acknowledged: true` and names the limitations before upload.
- `POST /api/source-template-sessions/{id}/source?filename=...` accepts one PDF or DOCX, applies configured limits, stores the original, and records the interpretation contract.
- `GET /api/source-template-sessions/{id}` returns interpretation, revision, approved snapshot, correction actions and draft links.
- `PATCH /api/source-template-sessions/{id}/interpretation/{item}` accepts `approve`, `correct` with `normalized_value`, or `reject`; correction history retains before/after snapshots.
- `POST /api/source-template-sessions/{id}/generate` requires approved items and creates a normal draft `Template` and `TemplateVersion` from only the approved snapshot.
- Starting **Create a template from a sample doc** always clears client workflow state; no prior session is restored from local storage or a latest-session lookup. Each acknowledged workflow gets a distinct server session. Existing sessions and generated drafts remain independent and are not deleted when a new workflow starts.
- `POST /api/source-template-sessions/{id}/compare` returns authorized source metadata, source URL, and the latest saved draft version. The editor opens the comparison page in a new tab after saving its current draft. It renders the original PDF (or converts DOCX with the configured local Word converter) beside the generated PDF in independent browser panes. It never reports identity without evidence.

Interpretation items distinguish deterministic structure from uncertain content. Headers, paragraphs, lists and table rows are `auto_accepted` when the bounded extractor has sufficient structural evidence; candidate variables, formulas and images remain `suggested` and require a user decision. Generation consumes `approved`, `corrected`, and `auto_accepted` items only. The review UI reports the structure breakdown and shows only items that need decisions.

DOCX interpretation now preserves body paragraphs and tables in source order, explicit run-level bold/italic/underline, font family/size/color, heading and list styles, paragraph alignment/spacing/indentation, section page size/margins, and text headers/footers where represented by standard OOXML. Tables become editable template tables with the first row used as column headings and remaining rows retained as sample data. Lists become editable semantic list blocks. Unsupported picture placement, floating objects, multi-column layouts, complex numbering, style inheritance not present directly on runs, and physical pagination remain limitations and must be reported; the parser does not invent page geometry from DOCX paragraph order. The implementation uses bounded Python standard-library ZIP/XML parsing and adds no package dependency.

Digital PDF extraction uses the already-pinned local `pypdf` reader to extract layout-mode text per source page, grouping wrapped lines into paragraph suggestions and keeping elements on their actual page. It does not infer bounding boxes when reliable geometry is unavailable; extraction provenance may therefore identify a source page without a box. Malformed PDF-like inputs retain a clearly weaker compatibility path; their text has no source box. Text-only PDFs still do not yield verified image, formula, or table structure, and this path is not OCR or general layout analysis. External AI is disabled unless explicitly requested and this implementation does not invoke a provider.

The comparison tab uses the saved draft version and browser PDF viewers, which provide independent native navigation, zoom and scrolling. DOCX comparison requires `word_converter_command` to be configured. The generated renderer, PDF conversion, exact visual matching, and native-reader correctness are not certified by this view.
