# Ingestion contract

The current ingestion slice accepts one bounded PDF, PNG, JPEG, or TIFF request through `POST /api/ingestions?filename=...`; the browser intake submits multiple files independently and displays each file's state. Raster headers are checked against the configured `max_image_pixels` limit (100,000,000 by default) before the object is stored or passed to downstream processing; this bounds declared pixel expansion, not decoder safety.

The service validates the extension, magic bytes, content type, and configured byte limit, rejects common PDF active-content declarations (`JavaScript`, actions, launches, embedded files, rich media, and XFA) in raw bytes and bounded FlateDecode streams before storage, then writes the original object to the configured storage backend and records a durable ingestion row. This PDF check is a bounded lexical gate, not a complete parser or malware scanner; malformed, oversized, or obfuscated content still requires the optional scanner and isolated downstream parser boundary. `GET /api/ingestions/{id}` returns routing/status metadata. `GET /api/ingestions/{id}/result` returns the versioned PageModel and Markdown derivative.

If `virus_scan_command` is configured, the service writes a short-lived temporary copy and invokes the executable plus that file path without a shell. Exit code zero is clean; nonzero, execution errors, and timeout reject the upload before storage. Scanner output is not returned to callers and the scanner receives only an explicit minimal allow-list of process, temporary-directory, and locale environment variables; application and deployment secrets are not inherited. An empty command disables the optional hook.

PDFs containing recognizable text operators are routed as `digital`; other accepted uploads are routed as `scan`. For PDFs whose page-object spans can be identified conservatively, each PageModel page also records `route: digital` or `route: scan`; if page association is uncertain, the document route is repeated rather than inventing page-level certainty. Callers may provide `ocr_language` and `ocr_engine` (`paddleocr` or `tesseract`) on upload. The versioned PageModel retains that request under `processing.ocr`; digital routes report OCR `skipped`, while the current service reports the selected scan engine as `unavailable` when its dependency is not installed rather than fabricating OCR text. If a configured local OCR command is present for a mixed PDF, it receives the bounded document and language, and only returned elements for pages marked `scan` are retained; digital-page text remains on the local path and `processing.ocr.requested_pages` records the dispatch scope. Parenthesized and simple hexadecimal `Tj` operands are recognized in the original bytes and in bounded FlateDecode streams (1 MiB compressed per stream, 4 MiB decompressed per stream, 16 MiB total). This is routing evidence, not a complete PDF parser or OCR result; the adapter protocol is page-aware but OCR accuracy and layout quality remain unverified. A conservative PDF page count is checked against `max_pages_per_document` (default 100), and `pages_total`/`pages_processed` are returned for progress. The contract path extracts uncomplicated text operators into text elements with stable synthetic point boxes and emits matching Markdown source comments. PNG, JPEG and TIFF scan headers provide bounded page dimensions; when available, the PageModel includes a full-page image element and matching source box. Other filters, complex PDF layout, fonts, transforms, scanned-page OCR and complete geometry remain delegated to isolated layout/OCR workers.

The contract is deliberately CPU/offline friendly and does not make provider calls. For simple digital text, PageModel pages also expose deterministic `layout.reading_order`, `layout.headings`, `layout.lists`, and explicit `table_row` roles for pipe-delimited rows. These are conservative marker-based annotations for local consumers, not a replacement for Docling reading-order, table segmentation, or arbitrary-PDF layout analysis. The bounded local PageModel extractor processes stored pages serially, publishes `running` with an incremented `pages_processed` value after each page, and finalizes successful extraction as `status=processed` with `pages_processed=pages_total`. The async extraction mode uses the durable job queue; the browser polls both the job and ingestion record, so multi-page progress is visible while work runs and remains queryable after a refresh. Page limits are enforced before storage. This satisfies the bounded local E8-05 progress contract; it is not OCR/layout progress. OCR/layout workers, Docling layout, PaddleOCR and complete provenance remain partial or pending Must stories.
