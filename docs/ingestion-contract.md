# Ingestion contract

The API accepts one bounded PDF, PNG, JPEG, or TIFF request through `POST /api/ingestions?filename=...`. The Digitization Intake UI currently selects one PDF per operation. After upload it queues the selected extraction schema, navigates to `/?digitization={document_id}&job={job_id}`, and displays job/page progress with the original PDF beside the current parser JSON. Beneath progress, the UI lists nine operational extraction tasks: PDF validation; page inspection and metadata capture; page classification; native content extraction; conditional OCR; content/provenance merge; layout and reading-order analysis; logical structure and complex-content reconstruction; and versioned JSON assembly and validation. The first three steps complete during upload. Later step status is not yet exposed; the progress bar reports aggregate job/page progress. The pane shows `physical_content` when available, otherwise the current PageModel. This is interim parser output, not the final schema extraction result; review actions are not part of this UI slice. The processing URL can be refreshed and continues polling the durable job and ingestion row. Raster headers are checked against the configured `max_image_pixels` limit (100,000,000 by default) before the object is stored or passed to downstream processing; this bounds declared pixel expansion, not decoder safety.

The service validates the extension, magic bytes, content type, and configured byte limit, then rejects common PDF active-content declarations (JavaScript, actions, launches, rich media, and XFA) in raw bytes and bounded FlateDecode streams before parsing. Embedded-file streams are allowed as opaque source content so their metadata can be indexed; recognized embedded-file payload bytes are excluded from lexical action scanning and are never decompressed, exported, or returned as attachment assets. Empty inline `/AA << >>` dictionaries are allowed because they register no additional action; populated or indirect `/AA` values remain rejected. PDFs are then opened with strict `pypdf` parsing in the existing credential-free, network-disabled worker under configured CPU, memory, wall-time, and output limits. Encrypted PDFs, PDFs missing a final EOF marker or catalog, malformed PDFs, zero-page files, and files over the configured page limit are rejected with a structured stage/code/message reason. The worker captures SHA-256 and bounded document metadata (title, author, creator, producer, dates, page dimensions, rotation, and count). Successful uploads persist this under PageModel `source.sha256` and `source.metadata`, then the original object and durable ingestion row are stored. The optional scanner remains a separate malware-scanning hook; PDF parsing is not a malware scan. `GET /api/ingestions/{id}` returns routing/status metadata. `GET /api/ingestions/{id}/result` returns the versioned PageModel and Markdown derivative.

If `virus_scan_command` is configured, the service writes a short-lived temporary copy and invokes the executable plus that file path without a shell. Exit code zero is clean; nonzero, execution errors, and timeout reject the upload before storage. Scanner output is not returned to callers and the scanner receives only an explicit minimal allow-list of process, temporary-directory, and locale environment variables; application and deployment secrets are not inherited. An empty command disables the optional hook.

PDFs containing recognizable text operators are routed as `digital`; other accepted uploads are routed as `scan`. PDFs with page-object spans are classified per page where possible. Callers may provide `ocr_language`, `ocr_engine` (`paddleocr` or `tesseract`), `ocr_mode`, and `ocr_preprocessing`. `ocr_regions` optionally supplies a JSON object of PDF page numbers to arrays of page-point rectangles; each rectangle must be inside its page, with at most 25 regions per page and 100 per upload. Region targeting is supported for PDF uploads. Auto mode targets scanned and mixed pages; explicit regions narrow OCR to those clips. The versioned PageModel retains the request under `processing.ocr`; unavailable engines and strict no-ML suppression are reported instead of fabricated text. Engine-specific `paddleocr_command` and `tesseract_command` settings dispatch to the corresponding local adapter; legacy `ocr_command` is identified as a custom engine. PDF pages or regions are rendered inside the isolated worker; OCR boxes are mapped from pixels to PDF page points. Mixed-page OCR remains an attributed candidate stream and native text is retained. Retry attempts, failures and regions below the engine-score threshold are reported, but scores are not calibrated correctness. The source upload remains unchanged.

The contract is deliberately CPU/offline friendly and does not make provider calls. For simple digital text, PageModel pages also expose deterministic `layout.reading_order`, `layout.headings`, `layout.lists`, and explicit `table_row` roles for pipe-delimited rows. These are conservative marker-based annotations for local consumers, not a replacement for Docling reading-order, table segmentation, or arbitrary-PDF layout analysis. The bounded local PageModel extractor processes stored pages serially, publishes `running` with an incremented `pages_processed` value after each page, and finalizes successful extraction as `status=processed` with `pages_processed=pages_total`. The async extraction mode uses the durable job queue; the browser polls both the job and ingestion record, so multi-page progress is visible while work runs and remains queryable after a refresh. Page limits are enforced before storage. This satisfies the bounded local E8-05 progress contract; it is not OCR/layout progress. OCR/layout workers, Docling layout, PaddleOCR and complete provenance remain partial or pending Must stories.

E22-103/104 implementation detail: each inspected PDF page retains a `native-text`, `scanned`, or `mixed-content` classification with character count, detected image coverage/count, configurable thresholds, and evidence. Compatibility routes remain `digital`/`scan`. The image metric follows basic image XObject placement operators and may miss inline images, form XObjects, or unusual streams; text bounding-box coverage and broad parser support are not claimed. Textless pages with no detected image placement follow the existing scan route and can be false positives. The canonical coordinate convention is PDF points with top-left origin and downward y, after crop-box clipping and clockwise page rotation. Page `source_geometry` retains original media/crop boxes in PDF user space and original geometry. Explicitly marked PDF-user-space element boxes are converted centrally while retaining their original box. Existing lightweight PDF extraction does not yet emit source boxes, so this normalization is available to adapters that do.

E22-201 through E22-204 physical content is exposed as `physical_content` schema version 2 alongside existing PageModel elements. When the optional `pdf-extraction` extra is installed and PyMuPDF succeeds, its raw page hierarchy is canonical for text: blocks contain line IDs, lines contain span IDs, and spans contain optional character IDs; every child also identifies its parent. IDs include page number, parser/version and source indices, so repeat extraction of the same PDF with the same parser version yields the same IDs. Parser upgrades may produce new IDs. `source_order` records the parser's native traversal order and does not claim validated reading order. PyMuPDF raw boxes/origins are retained with source coordinate labels; canonical boxes are transformed by the page rotation matrix and clipped to the rotated page bounds. With the optional parser absent or failing, the pypdf hierarchy remains available with parser/version-scoped IDs, but its estimated line/block grouping and missing text boxes are explicitly limited. Character records remain opt-in (`include_characters=true`). The canonical hierarchy has a 750 KB document budget; when exceeded, optional characters are removed first, then complete page subtrees are omitted with diagnostics so references never dangle. pdfplumber character/table observations and pdfminer.six layout observations remain separate and are not merged into canonical records. Parser comparison detail has a separate 1 MB document budget.

The bounded pypdf adapter provides links, annotations, bookmarks, attachment metadata and navigation. Images use authenticated `GET /api/ingestions/{id}/assets/{asset_id}` routes and content hashes. External links are metadata only; only `http`, `https`, and `mailto` URI schemes are returned as usable targets and no target is fetched. File-attachment annotations retain their page region and bounded file-spec metadata. Document-level `/Names/EmbeddedFiles` entries are returned in `physical_content.attachments` with filename, description, relationship, media type, declared size and source; annotation entries use the same metadata shape. The original PDF remains stored as uploaded, but attachment stream bytes are not read or exposed through the separate asset route. Attachment name-tree traversal is bounded to 1,000 entries, 2,000 nodes and depth 16; malformed or over-limit trees produce diagnostics. The active-content preflight continues rejecting JavaScript, launch/open actions, rich media, XFA and populated additional-action dictionaries; attachment payload bytes are treated as opaque and recognized embedded-file streams are excluded from lexical action scanning. This policy is not a malware scan; configured scanners and isolated parser resource limits remain separate controls. In the optional PyMuPDF canonical path, extraction requests `TEXT_COLLECT_STYLES`: span font flags preserve MuPDF-computed superscript, and character-style flags preserve parser-reported underline and strikeout when present. The span `font.superscript_source` identifies the MuPDF flag; `font.char_flags` and `style_evidence` retain decoration evidence and its source. Thin horizontal drawing paths geometrically near a span are retained separately as decoration candidates with source geometry and overlap; they do not override unknown/false parser style values. For E22-203, displayed raster images are exported from PyMuPDF image blocks as separate SHA-256-deduplicated assets, retaining each placement, page, source box, transform, dimensions and optional mask reference. PyMuPDF drawing paths retain their command items and geometry plus stroke/fill colors, width, dashes, line caps/joins, opacity, closure, sequence and clipping/group metadata. The visual model is capped at 2 MB; image binaries at 512 KB each and 2 MB total; image placements at 2,000/page; paths at 2,000/page and 20,000 drawing items/page. Limits produce diagnostics and omit whole trailing records. If PyMuPDF is missing or fails, the pypdf image/vector adapter remains as a lower-fidelity fallback. The drawing heuristic for text decorations is candidate-only and can include table/page rules or miss rotated, dashed, clipped, or unusually drawn decorations. Neither path claims exhaustive rendering-equivalent extraction: image blocks can omit clipped/non-displayed objects; PyMuPDF drawing reconstruction ignores some PDF visibility rules. PyMuPDF remains optional because its AGPL/commercial licensing decision is unresolved. E22-202 and E22-203 remain partial pending corpus review and licensing/runtime resolution; E22-204 remains partial pending attachment/action-boundary and end-to-end regression evidence.

## E22 logical model, JSON schema and export surfaces

PDF ingestion retains PageModel v1 and physical content v2, and adds a deterministic `logical_content` v1 analysis result when the isolated PDF inspection succeeds. The result endpoint returns both the original model and a typed `canonical_document` envelope when validation succeeds. Machine-readable schemas are available at `/api/schemas/e22-physical-content-v2.json`, `/api/schemas/e22-logical-document-v1.json`, and `/api/schemas/e22-canonical-document-v1.json`.

Authenticated clients can request `/api/ingestions/{id}/export` with `view=physical|logical|combined`, `scope=document|page`, `page_number=N` for page scope, and `format=json|jsonl|zip`. Exports are fully assembled before the configured output-size check; oversized output is rejected as a whole. ZIP places image assets in `assets/` and references them from the JSON. JSON contains metadata/references, not base64 binaries. The current cap is the smaller of `max_object_bytes` and 50 MB.

The JSON view in Digitization Intake shows the current canonical parser output beside the source PDF. It is an interim parsing artifact; it does not mean OCR accuracy, semantic structure, or final schema extraction has been approved. Logical/layout confidence values are rule evidence, not calibrated probabilities.

The OCR feature switches are `ocr_mode=auto|disabled|force`, `ocr_preprocessing` as bounded JSON for deskew, right-angle rotation, denoise and contrast, and optional PDF `ocr_regions` page-point rectangles. PDF page crops are rendered and mapped back to page-point coordinates. A retry can apply contrast and denoise alternatives; failure and low engine-score observations appear in `processing.ocr.recovery`. `strict_no_ml_mode=true` suppresses both engines regardless of the request. PaddleOCR requires explicit local model directories; model downloads are not performed during ingestion.
