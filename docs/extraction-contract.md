# Local extraction contract

`GET /api/extraction-schemas` lists the bundled invoice, receipt, and purchase-order schema starters, each with a sample URL. `GET /api/extraction-schemas/{id}` returns the editable domain schema; `GET /api/extraction-schemas/{id}/json-schema` returns its JSON Schema projection; `POST /api/extraction-schemas/validate` validates an edited domain schema without persisting it. `GET /api/extraction-schemas/{id}/sample` returns the versioned schema, a deterministic PageModel sample, and expected normalized field/table output. `POST /api/extractions/local` accepts a versioned PageModel plus either `schema_id` or an inline schema and returns an `ExtractionResult`-shaped response. An optional `calibration_profile` must be a validated `confidence-calibration-v1` isotonic profile generated from a separate labelled calibration corpus. When supplied, affected fields retain `raw_confidence` and expose the calibrated value in `confidence`; the response records the profile identifier. The same profile can be supplied to the ingestion extraction endpoint, including its durable async job payload. Profiles are data-only and cannot execute code or select arbitrary result paths.

`GET /api/extraction-engines` exposes the `extraction-engine-v1` registry. The bundled `local-label-extractor` is available offline and supports scalar fields, explicit delimited tables and provenance. Optional Docling and PaddleOCR descriptors report their installed/unavailable state. Python plugins can register an engine through the `docplatform.extraction_engines` entry-point group; each plugin must expose a bounded lowercase `id`, nonempty bounded `version`, declared capabilities, and `extract(page_model, schema, locale)`. IDs and capability names use `[a-z0-9][a-z0-9._-]*`; duplicate IDs are ignored in the public registry. Plugins must return `schema_version: 1`, object-valued fields/tables, confidence values in `[0, 1]`, and null-or-object source provenance. A field with a non-null original or normalized value must have non-null provenance; missing fields may use `source: null`. Non-null provenance must contain a positive page number and a finite positive four-coordinate box; optional element IDs must be strings. The API validates this envelope and rejects incompatible results; it never silently falls back to a different engine.

Layout adapters use the separate `layout-engine-v1` boundary in `app.layout.map_layout_output`: normalized pages carry page numbers, dimensions, coordinate systems, elements, reading order, roles, headings, lists, tables, and bounded source boxes. The mapper rejects duplicate IDs, invalid rectangles, unsupported roles, malformed page numbers, and over-limit results before they reach the PageModel. This is an adapter contract and local heuristic evidence only; Docling execution, OCR layout quality, arbitrary PDF reading order, rotation handling, and native layout review remain open.

The local extractor is deterministic and offline. It matches configured labels in text elements, retains the original and normalized values, records page/element/box provenance, emits a per-field confidence value, and reports required/type/minimum/maximum/pattern/checksum findings. Schema `totals` rules compare a scalar total with a configured table column and flag mismatches. Bundled invoice and purchase-order schemas also accept pipe-delimited line rows and return `tables.<name>.rows[].fields` with per-cell provenance. Numeric and date normalization uses the request locale (including comma-decimal locales such as `de-DE`); original values remain unchanged. Currency normalization uses `Decimal` and preserves two decimal places.

For E9-10, the local matcher includes small, explicit alias dictionaries for Arabic, Hindi, Thai, Chinese, and Japanese for the bundled invoice concepts (invoice number, invoice date, total and merchant). Regional locale tags use their base language for dictionary selection. Schema labels remain authoritative, aliases are deterministic and deduplicated, and no translation service or fuzzy matching is used. This satisfies the bounded label-dictionary contract; OCR accuracy, broader vocabulary and production multilingual quality remain separate evidence requirements.

For an uploaded document, `POST /api/ingestions/{id}/extract` applies the same local contract to its stored PageModel and returns that PageModel alongside the extraction result so a review client can resolve source elements without a second, potentially inconsistent fetch. Field and table-cell `source` values include the page number and, when available, the exact four-coordinate box; the review UI overlays that box in addition to highlighting the containing PageModel element. The endpoint does not mark data approved or persist a review snapshot.

Extraction results can be persisted and reviewed through `GET /api/extractions/{id}`, field correction with an expected revision, review state changes, and CSV correction export. `GET /api/extractions/{id}/export.json`, `/export.csv`, and `/export.xlsx` export field values with confidence, review status, validation and source coordinates. `POST /api/templates/{template_id}/render-approved` refuses anything except an explicitly approved result, preserving the closed-loop boundary.

`POST /api/extractions/{id}/webhook` sends an explicit JSON delivery to a configured allow-listed HTTP(S) host. The payload includes the result ID, status, revision and extraction result; an optional caller-provided secret produces an `X-DocPlatform-Signature: sha256=...` HMAC header. The default allow-list is empty, the request timeout is bounded, and the endpoint does not retry or automatically publish on approval.

This is a deterministic local contract, not calibrated production extraction by default. `scripts/calibrate_extraction.py` creates a reusable isotonic profile from an explicitly supplied calibration corpus, records the corpus source, SHA-256 and record count, and `confidence_calibration_path` can load an independently reviewed profile at startup. The repository fixture is not a representative held-out evaluation set and no production calibration claim is made from it. Confidence values remain heuristic unless an independently reviewed profile is configured. OCR/layout engines, broad table-layout handling, export-delivery retries/history, native page rendering and multilingual production accuracy remain incomplete even though bounded local tables, JSON/CSV/XLSX exports, allow-listed webhook delivery, review, and approved-result binding are covered by their respective contracts.

## Benchmark contract

`python scripts/benchmark_extraction.py --input <labelled-jsonl> --output artifacts/extraction-benchmark.json` runs the local extractor without network or model calls. Each JSONL record supplies `schema_id`, `page_model`, and `expected.fields`; optional `expected.tables.<name>.rows` enables table row and column metrics. The report contains document counts, scalar normalized/original exact-match rates, table row/column rates, confidence calibration (mean confidence, empirical accuracy, Brier score, absolute calibration error, and ten fixed reliability bins), missing predictions, invalid predictions, and per-field results for every schema. The checked-in fixture includes both a matching invoice and an intentionally mismatched total so the low-confidence/failed-rule bin is exercised; it remains a deterministic contract fixture, not a held-out accuracy claim. Replace or supplement it with a labelled evaluation corpus before making production accuracy or confidence-calibration claims.
