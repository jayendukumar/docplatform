# Durable jobs contract

On Windows, supervisor-triggered termination uses `taskkill /T /F` so converter and OCR descendants are not left behind when a wall-time or output limit fires. This is a hardening slice; native deployment enforcement and stable exhaustion evidence remain open.

`POST /api/jobs` accepts `render` or `extraction` payloads and returns a durable job ID. `GET /api/jobs/{id}` provides `queued`, `running`, `done`, or `failed` state, attempts, timestamps, result, and sanitized error information. `POST /api/jobs/{id}/run` claims a queued or expired-lease job and executes it in a credential-free child process under configurable wall-time, CPU, address-space and output limits. Synchronous render and approved-result render use the same child runner. POSIX children apply `RLIMIT_CPU` and `RLIMIT_AS`; a POSIX-only regression runs a real CPU-bound nested engine, verifies it is stopped before the wall limit, and verifies a subsequent render completes. Windows children are attached to a Job Object with per-process CPU and memory limits and kill-on-close behavior, with parent-side CPU-clock and working-set watchdogs as additional termination paths. The parent timeout and serialized-output guard remain the portable outer boundary; real-child regressions confirm that an oversized serialized result is rejected and a subsequent child still completes, and the watchdog contract reports memory-limit termination without poisoning the supervisor. Compose adds independently configurable worker-service ceilings through `DOCPLATFORM_WORKER_CPU_LIMIT` (default `2.0` CPUs), `DOCPLATFORM_WORKER_MEMORY_LIMIT` (default `768m`) and `DOCPLATFORM_WORKER_PIDS_LIMIT` (default `256`); these protect the render and extraction service boundary and do not replace per-job limits. On the current Windows development host, direct Job Object attachment succeeds, but a tight-loop CPU exhaustion probe did not yield stable native per-process termination evidence; deployment-level enforcement across all supported runtimes and a stable native exhaustion fixture remain open, so E12-02 is still partial.

`POST /api/templates/{template_id}/render` renders small templates synchronously. When the definition exceeds `sync_render_max_blocks` (100 by default), or the request sets `async: true`, it creates a queued render job and returns its polling URL. The threshold is a bounded routing default, not a throughput benchmark.

Job rows and leases are persisted in PostgreSQL, so status survives API process recreation. The default Compose topology runs the web API with `job_worker_enabled=false` and starts separate `render-worker` and `extraction-worker` services. Each standalone process claims only its own job kind through the same PostgreSQL lease contract and reuses the bounded executor exposed by the application. Scale them independently with `docker compose up --scale render-worker=N --scale extraction-worker=M`; the API remains responsible for enqueueing and polling. The reproducible `scripts/benchmark_compose_workers.py` command warms each topology, runs repeated eight-job/80-block queued-render samples, polls job states concurrently, and compares medians for one and two render-worker replicas. The report retains every sample and warm-up measurement; a faster median is local evidence only and is not a production capacity guarantee. For a single-process deployment, `job_worker_enabled=true` still enables the bounded lifespan supervisor with independent `job_worker_render_count` and `job_worker_extraction_count` pools. Lease recovery, child limits and result persistence are shared by both modes. Retries/DLQ, native cgroup enforcement, general capacity objectives and production authorization remain pending. The child denies socket connection attempts and receives no database or storage credentials.
